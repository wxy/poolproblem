# pnpm owner command isolated E2E

Run from any directory on macOS with Swift installed:

```sh
sh docs/verification/pnpm-owner-recipe/run.sh
```

The script creates a task-specific `$TMPDIR/poolproblem-pnpm-owner.*` directory, compiles the actual `DiskReservoirCore` sources with Swift and Clang module caches inside it, and launches the controlled `fixture.sh` with isolated `HOME`, `store`, and data directory. The input fixture implements `pnpm store path` and `pnpm store prune`; it never invokes installed pnpm. Temporary files are removed at exit. The repeatable output artifact is [`last-run.log`](last-run.log).

Observed result after the Cleaner fix: 34 assertions pass. They cover exact store probing, successful prune preserving the store directory, separate owner command history and absent fabricated clean log, nonzero exit, target change and invalid target refusing prune, bounded output, timeout stopping the wrapper and ordinary child processes, and legacy/default recipe guards. Thirteen assertions exercise persisted aggregates through the real `Cleaner` and `FileManagerFileDeleter`: with `scan.volumeURL` set to `/`, the configured temporary HOME's pnpm tree survives while `.npm` is deleted; a second aggregate from a different historical temporary HOME likewise preserves its pnpm tree while `.cache/uv` is deleted; a third aggregate includes that historical home's `Library` parent and all three remaining approved default roots. The parent and pnpm sentinel survive, while `.npm`, CocoaPods, and Homebrew caches are deleted. Outcome and durable clean log checks ensure protected targets are not reported as cleaned. No user pnpm store is touched. The separate journal harness passes nine assertions for durable attempt and completion recording; see [`JOURNAL-REPORT.md`](JOURNAL-REPORT.md). It does not establish that the real pnpm command behaves identically or that the macOS UI renders correctly. Live UI acceptance remains open.

Fail-first evidence: after adding the five Cleaner assertions and before changing the implementation, `sh docs/verification/pnpm-owner-recipe/run.sh` exited 133. [`cleaner-before.log`](cleaner-before.log) records the safe `.npm` cache being removed, then `Fatal error: legacy pnpm tree survives Cleaner`. The command, temporary HOME, aggregate input, and assertions are in `run.sh` and `OwnerCommandE2E.swift`; rerunning the current script produces [`last-run.log`](last-run.log). The failure modes considered before implementation were an old persisted pnpm root or descendant being deleted when volume and HOME differ, a mixed aggregate deleting protected targets, an overbroad guard blocking unrelated caches, an early waterline stop masking the deletion path, and a result-only assertion missing real filesystem deletion. The test checks the actual file tree and durable log with a large deficit.

Second fail-first evidence: after adding the historical HOME scenario and before broadening the path guard, the same command exited 133. [`mismatched-home-before.log`](mismatched-home-before.log) records the unrelated `.cache/uv` directory being deleted, then `Fatal error: historical-home pnpm tree survives Cleaner`. The second temporary HOME is a sibling of the configured temporary HOME under the task directory. Failure modes considered were a stale absolute path from a prior HOME, symlink or `..` aliases hiding the pnpm segment, an overbroad guard suppressing safe caches, and a result-only check missing deletion. The guard now checks standardized input and resolved canonical paths for the exact `Library/pnpm` directory segment, while retaining the configured home's canonical-root check for aliases into a symlinked pnpm root. The run checks actual file survival and safe-cache deletion.

Third fail-first evidence: after adding a persisted aggregate with the historical home's `Library` parent and before adding the positive allowlist, the same command exited 133. [`parent-before.log`](parent-before.log) records all approved default caches being deleted, then `Fatal error: historical Library parent and pnpm survive Cleaner`. This proved that a descendant-only pnpm guard does not stop recursive deletion of an ancestor. Failure modes considered were stale parent targets, old extra roots, accidental denial of default caches, and mismatch between actual deletion and logs. The built-in `package-manager-caches` family now permits only exact standardized current default roots, checked for each target in Cleaner and manual AppService cleanup. The broad pnpm path guard remains as backup. User-configured cache roots use the separate manual-only custom recipe in the app.

Source inspection: default package manager paths exclude `~/Library/pnpm`; `Cleaner` checks old snapshot paths against the positive default-root allowlist and the broad pnpm path guard, with configured home supplied from `StoragePaths.homeDirectory` by GUI, CLI, and MCP callers. Manual AppService cleanup applies the same checks. GUI scan and package/project recipe roots use the same configured home. The dedicated command has no raw path deletion fallback. The custom package-manager recipe follows a separate manual-confirmation path; its own policy remains distinct from the built-in family's allowlist.

## Real pnpm smoke test

Run `docs/verification/pnpm-owner-recipe/run-real-pnpm.sh` with pnpm on `PATH`. The script gives pnpm an isolated task-specific `HOME`, XDG directories, and `PNPM_HOME`. It reads `pnpm store path` and refuses to run `prune` unless that path is inside the temporary fixture. Its input is an empty store; the output artifact is [`real-pnpm-last-run.log`](real-pnpm-last-run.log). On 2026-09-27, installed pnpm resolved its store within the fixture and `prune` exited successfully, reporting 0 packages removed. This verifies real command launch and target isolation, not meaningful space recovery from a populated store.

An attempt to populate the temporary store using `pnpm store add` with a local directory failed in the installed pnpm version (`pkgResponse.fetching is not a function`). The final smoke test therefore uses an empty store and makes no claim about populated-store prune behavior. No command was run on the real user store.
